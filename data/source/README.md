# Reproducibility source inputs

`delhi_wards_boundaries.geojson` is the checked-in ward geometry used by `scripts/build_ward_infra.js`.

The one-off crash-report preparation scripts expect these optional directories when their source extracts are available:

- `data/source/crash_report_2023/`
- `data/source/crash_report_2024/`

They can instead be supplied through `CRASH_REPORT_2023_SOURCE` and `CRASH_REPORT_2024_SOURCE`. Ward geometry can be overridden with `DELHI_WARDS_GEOJSON`.

Do not add private, access-controlled, or unlicensed files here.

## Pedestrian overbridge snapshot

`osm_pedestrian_overpasses_delhi_raw.json` is the raw OpenStreetMap/Overpass snapshot used by `scripts/build_pedestrian_overpasses.js`. The reproducible query selects `highway=footway|path|steps` ways tagged `bridge=yes|footbridge`; connected segments are grouped, nearby components merged within 45 metres, converted to centroids, and filtered to the dashboard district polygons. This is a mapped-feature inventory, not an official completeness register.

## Traffic signals, pedestrian crossings, hospitals, and footway/sidewalk snapshots (2026-08-06)

`osm_traffic_signals_crossings_delhi_raw.json`, `osm_hospitals_delhi_raw.json`, and `osm_footways_delhi_raw.json` are raw OpenStreetMap/Overpass snapshots fetched by `scripts/fetch_osm_infra_snapshots.js` and processed by `scripts/build_infra_extras.js`. Queries (bounding box `28.35,76.80,28.95,77.40`, matching the dashboard's own district-boundary extent):

- Traffic signals/crossings: `node[highway=traffic_signals]`, `node[highway=crossing]`.
- Hospitals: `node|way|relation[amenity=hospital]` (way/relation centroid via Overpass `out center`).
- Footways: `way[highway=footway]`, `way[highway=pedestrian]`, `way[footway=sidewalk]`, fetched in four geographic quadrants (Overpass's public instance times out on the full bbox in one request) and deduplicated by way ID before use.

All four are filtered to the dashboard's 15 district polygons (points/way-midpoints outside every polygon are dropped, same convention as the pedestrian-overbridge snapshot). Footway data is *not* shipped to the browser as line geometry — `build_infra_extras.js` computes total length (km) and density (km per km²) per district at build time instead, written to `data/delhi_footway_coverage.json`. This is a mapped-feature inventory, not an official completeness register; re-fetch with `node scripts/fetch_osm_infra_snapshots.js` then `node scripts/build_infra_extras.js`.

`osm_street_lamps_delhi_raw.json` (`highway=street_lamp`, 1,529 nodes fetched, 1,457 within district polygons) is shown as its own map layer ("Street lamps (OSM)"), kept separate from the existing PAPL Open Transit Survey point layer, since OSM only has point locations and PAPL only publishes district totals — there's no point-for-point reconciliation possible between the two.

## Combined PAPL + OSM streetlight metric (2026-08-06)

`data/streetlights_combined_by_district.csv`/`.json` (generated by `scripts/build_infra_extras.js`) *does* reconcile the two at the district level, where a real merge is possible: for the 9 districts the PAPL survey actually covers (`surveyPoints >= 10`), `combined_count` is PAPL's `totalLights` — the far more complete, professionally surveyed figure (e.g. Central: 8,173 PAPL vs. 29 OSM-tagged lamps in the same district). For the 3 districts PAPL has no survey data for but OSM has at least some tagged lamps (Dwarka, North-West, Rohini), `combined_count` falls back to the OSM count. The remaining 3 districts (North-East, Outer, Outer North) have neither and are correctly left `null`, not a fabricated zero. Every row's `combined_source` column says exactly which one was used — PAPL's number and OSM's fallback are never blended into one unattributed figure. Also available as a "Streetlights (PAPL + OSM combined)" choropleth/bivariate option on the interactive map, alongside the unchanged, PAPL-only "Streetlights" metric.

## Ward-wise land use (2026-08-06)

`data/landuse_by_ward.csv` (generated by `scripts/build_landuse_wards_csv.js` from `osm_landuse_delhi_raw.json`, 9,908 unique `landuse=*`-tagged ways) reports per-ward area (km²) and share of ward area for six categories (`residential`, `commercial`, `industrial`, `institutional`, `green_open`, `other`) via real polygon-overlap area computed with `@turf/turf`, not a point-in-polygon approximation.

An official Delhi ward-wise land-use dataset was searched for and deliberately not used: DDA has no machine-readable land-use layer, only PDF master-plan maps. The only vectorized version found is a [community extraction](https://github.com/rajesvariparasa/layers_draft_delhi_master_plan_2041) of the **draft** (not adopted) Master Plan 2041 -- no explicit license, and the extracting author discloses both attribute-data loss (sub-categories collapsed) and geometric distortion in several layers. Used OSM instead, which is current (not a draft proposal) and ODbL-licensed, at the cost of being sparser.

**Real, load-bearing caveat**: OSM `landuse=*` tagging covers only ~23.4% of ward area on average (see each row's `mapped_pct`) -- most land in Delhi is simply untagged in OSM, not unmapped/undeveloped. Never read `100% - mapped_pct` as "vacant land." Also scoped to `way`-tagged features only (9,908 of 11,366 total landuse features in the fetch snapshot); the remaining 1,458 `relation`-tagged multipolygons need outer/inner ring assembly this script doesn't attempt, so they're excluded rather than approximated. Regenerate with `node scripts/build_landuse_wards_csv.js` after re-fetching `osm_landuse_delhi_raw.json` (`way["landuse"]` over the same bounding box as the other OSM snapshots here, fetched in the same four quadrants for the same rate-limit reasons).

The same script also writes `data/delhi_landuse_simplified.geojson` (coordinates rounded to 5 decimal places, `turf.simplify`d at 0.0001° tolerance -- full precision would add ~3.4MB to the page) for the interactive map's "Land use" polygon layer. Same six categories, same coverage caveat, both restated in every polygon's popup so the map layer can't be misread differently from the CSV.

## Road and footway "size" data (2026-08-06)

`data/road_sizes.csv` and `data/footway_sizes.csv` (generated by `scripts/build_road_footway_sizes_csv.js` from `osm_major_roads_delhi_raw.json` and `osm_footways_delhi_raw.json`) report per-segment classification (`highway=*`, always tagged), lane count (`lanes=*`, tagged on 33.7% of major-road segments), and explicit width (`width=*`, tagged on 0.2% of roads and 0.7% of footways). No dedicated official Delhi dataset with actual measured per-segment road/footpath widths was found: [data.gov.in's "surfaced length of PWD roads by width"](https://www.data.gov.in/catalog/stateut-wise-surfaced-length-other-pwd-roads-width-india) is a state-level aggregate behind an API key, not per-road-segment Delhi geometry, so it wasn't pulled in. Rather than estimate a width from a road's classification tier, missing `width_m`/`lanes` are left blank -- never filled with an assumed value. Regenerate with `node scripts/build_road_footway_sizes_csv.js` after re-fetching the raw snapshots.
